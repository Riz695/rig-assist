# Fine-tuned embedder: what the eval shows

Commentary on [`finetune.md`](finetune.md) (generated by `make eval`; this file is written
by hand and isn't regenerated). Run on 2026-10-26 at commit `e16dd97`: the served base
model, the base model exported to fp32, and the fine-tuned model (`ft-inbatch-e3-s1`,
registered as `rig-assist-embedder` v1), each in dense, hybrid and hybrid + rerank, on the
frozen eval set (42 answerable questions, 5 unanswerable). Same chunks, same BM25, same
reranker; only the embedding model and its Qdrant collection change.

## Results

| mode | served base MRR@10 | fine-tuned MRR@10 | Hit@1 | Hit@5 | better / worse | sign test p |
|---|---|---|---|---|---|---|
| dense | 0.766 | **0.813** | 27 → 30 | 38 → 39 | 8 / 5 | 0.58 |
| hybrid | 0.804 | **0.827** | 31 → 32 | 36 → 39 | 4 / 1 | 0.38 |
| hybrid + rerank (served) | **0.865** | 0.853 | 33 → 32 | 41 → 41 | 0 / 1 | 1.00 |

1. **The first stage gets better; the served pipeline doesn't.** Fine-tuning raises dense
   MRR@10 by 0.047 and hybrid by 0.023, and hybrid finds 3 more answers in the top 5.
   With the reranker on (the served mode), the result is the same or one question worse.
   A likely reason: the cross-encoder re-scores the top 20 candidates, and both first
   stages already put nearly every answer page in those 20 (hybrid + rerank Hit@5 is
   41/42 either way), so the final order is the reranker's, not the embedder's.
2. **None of the differences is statistically meaningful.** In dense mode, 8 questions
   improve and 5 get worse; a split at least that uneven happens 58% of the time by chance
   (exact sign test). 42 questions can only show large effects: with no losses at all, it
   takes 6 improved questions to reach p < 0.05 and 8 to reach p < 0.01.
3. **The gain is smaller than on the validation set.** Validation MRR@10 (synthetic
   queries on held-out pages) rose from 0.591 to 0.675; the hand-written questions gain
   0.047 in dense mode. A likely reason: the model learned the LLM generator's way of
   asking as well as the manuals' vocabulary, and real questions are worded differently.
4. **Precision isn't a factor.** The served base (fastembed's fp16 file) and our fp32 export
   of the same model rank every question identically (vectors match to a cosine of
   0.999999). So fp32 vs fp16 doesn't explain anything here, and the fine-tuned export
   could be converted to fp16 to halve its size (134 MB → 67 MB).
5. **Scores shift, so thresholds don't transfer.** The fine-tuned model gives lower cosine
   scores: the refusal threshold tuned on this set drops from 0.667 to 0.408, and v1's
   fixed 0.6 would refuse most answerable questions. The served pipeline has no score
   gate today (the LLM decides "not found"), but any future gate must be tuned per model.

## Decision

Keep the base model as the served default (`EMBEDDING_MODEL` unchanged): in the served
mode (hybrid + rerank) fine-tuning doesn't help, and it adds a model to ship. The
fine-tuned model is one setting away
(`EMBEDDING_MODEL=data/models/finetuned/ft-inbatch-e3-s1/model-onnx`) and is the better
choice for a deployment without the reranker (2 s → 0.09 s per query), where its first-stage
gain matters.

## What would make the comparison more decisive

- More hand-written questions (100+): the current set can't separate a 0.02–0.05 MRR gain
  from noise.
- Training queries closer to real ones (technician questions from logs, if any exist).
- Fine-tuning the reranker, since the reranker sets the final order in the served mode.
